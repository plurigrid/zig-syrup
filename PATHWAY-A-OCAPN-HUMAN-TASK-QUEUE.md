# Pathway A: OCapN-Native Human Task Queue

> Using existing zig-syrup continuation infrastructure as the backbone for dispatching tasks to human workers.

## 2. PromiseKey → Human Task Assignment

### Question 1: How does an OCapN PromiseKey map to a human task assignment?

**Answer: A PromiseKey IS the task assignment. Capability = permission to act on behalf of the account holder.**

The existing `PromiseKey` in `src/ghostty_ix_continuation.zig` (lines 29-40) is already an unforgeable capability handle:

```zig
// src/ghostty_ix_continuation.zig
pub const PromiseKey = struct {
    id: u64,          // Unforgeable capability seal
    created_at: i64,  // When the task was created
    phase: u8,        // 0=assigned, 1=paused, 2=resumed, 3=completed
};
```

**Mapping to human tasks:**

| PromiseKey field | Human task meaning |
|---|---|
| `id` | Task assignment ID. Generated by `ContinuationExecutor.generateCapability()` via SplitMix64 PRNG — unforgeable, non-guessable. Holder of this ID can act. |
| `created_at` | Task creation timestamp (milliseconds). Used for SLA tracking. |
| `phase` | Task lifecycle: **0** = assigned to worker, **1** = worker paused (e.g., waiting for materials), **2** = worker actively executing, **3** = completed and awaiting validation |

**Capability semantics:** Possession of the PromiseKey `id` is the ONLY authorization needed. There are no passwords, no OAuth tokens, no API keys. If you have the ID, you can act. If you don't, you can't. This is the OCapN security model — capabilities are unforgeable references.

**The `ContinuationExecutor` (line 119-140) already manages the full lifecycle:**

```zig
// Existing executor flow — no changes needed
executor.pause(cmd)          // → Creates PromiseKey, stores ContinuationState
                             //   "A task has been created and assigned"
executor.resumeExecution(id) // → Looks up by PromiseKey.id, marks resumed
                             //   "Worker is executing the task"
```

**Account hold mechanism:** The PromiseKey's `phase` field transitions enforce account holds:
- Phase 0→1: Funds are placed on hold (temporary authorization created)
- Phase 1→2: Worker begins; hold remains active
- Phase 2→3: Task completes; hold is either captured (payment) or released (cancellation)
- If PromiseKey is never resumed (phase stays 1): hold auto-expires based on `created_at` + TTL

## 3. ContinuationState → Full Task Context

### Question 2: How does ContinuationState serialize the FULL context a human needs to perform a one-shot task?

**Answer: Two ContinuationState types compose — the pipeline state from `continuation.zig` carries the task steps, while the IX state from `ghostty_ix_continuation.zig` carries the execution frame.**

### 3a. Pipeline-level context (`src/continuation.zig`)

The existing `ContinuationState` (lines 86-140) serializes to a Syrup record `<continuation id steps current status metadata timestamp>`:

```zig
// src/continuation.zig — already exists
pub const ContinuationState = struct {
    id: ContinuationId,          // Unique task ID (UUID)
    steps: []const Step,          // Ordered sub-tasks the human must complete
    current_step: usize,          // Which step the worker is on
    status: ContinuationStatus,   // initialized/running/paused/completed/failed
    metadata: ?syrup.Value,       // ARBITRARY Syrup value: address, photos, notes
    created_at: i64,
    updated_at: i64,
};
```

**For a human task, each `Step` (lines 60-84) is a concrete instruction:**

```zig
// Example: "Deliver groceries" task with 3 steps
const steps = [_]Step{
    .{ .name = "pick-up-from-store",   .trit = .plus },  // Generator: create/acquire
    .{ .name = "deliver-to-address",   .trit = .zero },  // Coordinator: transport/route
    .{ .name = "confirm-with-photo",   .trit = .minus }, // Validator: verify/check
};
```

Each step's `.state` field (a `?syrup.Value`) can carry arbitrary structured data — addresses, item lists, photos, signatures — because Syrup supports nested records, dictionaries, lists, bytes, and tagged values.

### 3b. Execution frame context (`src/ghostty_ix_continuation.zig`)

The IX `ContinuationState` (lines 43-72) captures the worker's execution context:

```zig
// src/ghostty_ix_continuation.zig — already exists
pub const ContinuationState = struct {
    promise: PromiseKey,          // The capability handle
    command_type: CommandType,     // What kind of task
    args: []const u8,             // Task description (serialized)
    saved_memory: []const u8,     // Attached context (photos, documents, etc.)
    registers: RegisterState,     // Worker state metrics
    stack_depth: u32,             // Recursion depth (humans hiring humans)
    resumed: bool,                // Has worker started?
};
```

The `RegisterState` (lines 74-79) maps to human task metrics:

| Register | Human meaning |
|---|---|
| `phi` | Task complexity / integration difficulty (0.0 = trivial, 1.0 = complex) |
| `valence` | Urgency / emotional priority (-1.0 = low, +1.0 = emergency) |
| `fisher_rao` | Information asymmetry between requester and worker |
| `dominant_trit` | Worker role classification: -1=Validator, 0=Coordinator, +1=Generator |

### 3c. One-shot interaction cue

A one-shot task is a ContinuationState where:
1. `steps.len == 1` (single instruction)
2. The step's `.state` contains ALL information the human needs
3. The step's `.trit` classifies what TYPE of action is needed
4. The `StepResult` is either `.success` (done) or `.failure` (couldn't complete)
5. There is no `.yield` — no partial completion, no pause-and-resume

The existing `Pipeline.step()` method (lines 196-214) already handles this:

```zig
// One-shot: single step, immediate result
pub fn step(self: *Pipeline, input: syrup.Value) StepResult {
    if (self.state.isComplete()) return .{ .success = input };
    const step_fn = self.step_fns[self.state.current_step];
    const result = step_fn(input, self.allocator);
    // ... status transitions happen automatically
}
```

### 3d. Syrup serialization for wire transport

The entire task context serializes to bytes via `ContinuationState.toSyrup()` (lines 107-131), which produces a Syrup record that can be:
- Sent over CapTP to a worker's device
- Content-addressed via `computeCid()` from `src/syrup.zig` (line ~1580) for deduplication
- Decoded zero-copy on the receiving end via `Parser` (line ~600)

## 4. GF(3) Worker Classification

### Question 3: How do GF(3) trits classify human workers?

**Answer: The triadic PRNG system in `src/splitmix_trit.zig` directly maps to three worker roles. Each task AND each worker has a trit. Tasks must be matched to workers whose trit complements.**

### 4a. The three worker roles

From `src/splitmix_trit.zig` (lines 34-38):

```zig
pub const Trit = enum(i8) {
    minus = -1,   // Validator   (ChaCha, Red)   — checks, inspects, verifies
    ergodic = 0,  // Coordinator (SplitMix64, Green) — routes, dispatches, manages
    plus = 1,     // Generator   (Rybka, Blue)   — creates, builds, assembles
};
```

**Concrete human examples:**

| Trit | Role | TaskRabbit equivalent | Action verbs |
|---|---|---|---|
| **+1 (Generator)** | Creator/Builder | Handyman, assembler, mover | Build, install, create, deliver |
| **0 (Coordinator)** | Router/Dispatcher | Project manager, team lead | Assign, route, schedule, coordinate |
| **-1 (Validator)** | Checker/Inspector | QA inspector, photographer | Verify, inspect, confirm, photograph |

### 4b. GF(3) conservation law

From `src/splitmix_trit.zig`:

```zig
pub fn isConserved(self: *const SplitMixTrit) bool {
    const delta = @as(i64, self.trit_sum) - @as(i64, self.component_sum);
    return @mod(delta, 3) == 0;
}
```

**Conservation property for `SplitMixTrit`:** the emitted trits must equal the accumulated
source trits modulo 3, because each step is defined as `c + s + r` in GF(3).

For task queues, that means any higher-level balancing rule has to be enforced by queue
structure itself. `SplitMixTrit.isConserved()` only verifies the trit combiner stayed
faithful to its three input streams.

- A Generator (+1) task requires a Validator (-1) task to balance
- Every creation must be verified
- A Coordinator (0) task is self-balancing (neutral)

**Example balanced cycle:**
```
  Handyman builds shelf  (+1, Generator)
+ Inspector photographs  (-1, Validator)
= 0 (balanced, task cycle complete)
```

**Example with coordinator:**
```
  Project manager assigns (-1 + 1 = 0, Coordinator)
+ Mover delivers items   (+1, Generator)
+ QA checks delivery     (-1, Validator)
= 0 (balanced)
```

### 4c. Worker classification via `SplitMixTrit.opine()`

From `src/splitmix_trit.zig` (lines 280-295):

```zig

    // Deterministic: same seed + same proposition = same trit

```

A worker's trit can be computed deterministically from their identity (seed) and the task proposition. This means:
- Worker A with seed 1069 always gets the same trit for "deliver groceries"

### 4d. Color-coded task visualization

From `SplitMixRGB.nextBiased()` (lines 393-411):

- Coordinator tasks glow **green** (G-channel boosted)

## 5. Humans Hiring Humans: Recursive Task Delegation

### Question 4: What is the "humans hiring humans" recursion? How does a Tasker with a PromiseKey spawn sub-tasks?

**Answer: The `ContinuationExecutor` in `ghostty_ix_continuation.zig` already supports this via `pause()` → derived PromiseKeys, and `HomotopyPath` connects parent→child chains.**

### 5a. The recursion mechanism

The `ContinuationExecutor` (lines 119-197) manages a `continuations` map and generates new PromiseKeys:

```zig
pub const ContinuationExecutor = struct {
    continuations: std.AutoHashMapUnmanaged(u64, *ContinuationState),
    paths: std.ArrayListUnmanaged(HomotopyPath),
    seed: u64,        // SplitMix64 seed for capability generation
    next_promise_id: u64,
    // ...
};
```

**Recursion flow:**

1. **Requester** creates a task → `executor.pause(cmd)` → gets `PromiseKey_A`
2. **Worker A** (a Coordinator, trit=0) receives `PromiseKey_A`, sees the task is too big
3. **Worker A** calls `executor.pause(sub_cmd)` → gets `PromiseKey_B` (derived from same seed lineage)
4. **Worker A** assigns `PromiseKey_B` to **Worker B** (a Generator, trit=+1)
5. **Worker B** completes the sub-task → `executor.resumeExecution(PromiseKey_B.id)`
6. **Worker A** sees sub-task complete, completes their own → `executor.resumeExecution(PromiseKey_A.id)`

The `stack_depth` field in IX `ContinuationState` (line 68) tracks recursion depth:

```zig
stack_depth: u32,  // 0 = top-level task, 1 = first delegation, 2 = sub-delegation, ...
```

### 5b. HomotopyPath connects the delegation chain

The existing `HomotopyPath` (lines 82-101) traces execution trajectories:

```zig
pub const HomotopyPath = struct {
    id: u64,
    states: std.ArrayListUnmanaged(ContinuationState),
    t: f32,           // Path parameter t ∈ [0,1]
    verified: bool,   // Has the full chain been validated?
};
```

**For human delegation:**
- `states[0]` = original requester's ContinuationState
- `states[1]` = Worker A's (coordinator's) state after delegation
- `states[2]` = Worker B's (generator's) execution state
- `t` tracks progress: 0.0 = just assigned, 0.5 = sub-task in progress, 1.0 = fully complete
- `verified` = the Validator (-1) has confirmed the entire chain

The existing `createHomotopyPath()` (lines 172-197) already links two states:

```zig

    // For task delegation: links parent task → child task

```

### 5c. GF(3) conservation across delegation depth

At each delegation depth, the GF(3) sum must be tracked:
- Coordinator (0) delegates to Generator (+1) and Validator (-1): sum = 0 ✓
- Generator (+1) delegates to two sub-generators: sum = +2 ≡ -1 (mod 3), needs a Validator to balance

The queue can maintain its own running GF(3) balance, but `SplitMixTrit.isConserved()`
is a narrower check: it verifies the additive combiner has not drifted from the three
underlying PRNG streams.

### 5d. Concrete "humans hiring humans" example

```
Task: "Renovate kitchen" (Coordinator task, trit=0)
  ├─ PromiseKey_A → Project Manager (Coordinator, 0)
  │   ├─ PromiseKey_B → Plumber (Generator, +1) — install sink
  │   ├─ PromiseKey_C → Electrician (Generator, +1) — rewire outlets
  │   ├─ PromiseKey_D → Painter (Generator, +1) — paint walls
  │   └─ PromiseKey_E → Inspector (Validator, -1) — inspect each
  │
  │  GF(3) check: 0 + (+1) + (+1) + (+1) + (-1) = +2 ≡ -1 (mod 3)
  │  → System requires one more Validator to balance
  │  → Auto-spawns PromiseKey_F → Final Inspector (Validator, -1)
  │  → New sum: -1 + (-1) + (+1) + (+1) + (+1) + 0 = +1... 
  │
  │  Actually: The GF(3) conservation is checked per CYCLE, not per tree.
  │  Each Generator→Validator pair forms a balanced cycle.
  │  Plumber(+1) + Inspect-plumbing(-1) = 0 ✓
  │  Electrician(+1) + Inspect-electrical(-1) = 0 ✓
  │  Painter(+1) + Inspect-paint(-1) = 0 ✓
  └─ Total: All cycles balanced ✓
```

## 6. BeliefSet / Grove Spheres → Authorization Model

### Question 5: How does the BeliefSet/Grove Sphere model track what a temporary worker BELIEVES they're authorized to do vs what they actually are?

**Answer: Grove Spheres from `src/continuation.zig` are ordered possible worlds. The innermost sphere (actual world) contains the REAL authorization. Outer spheres contain the worker's BELIEFS about their authorization. AGM revision updates beliefs when reality changes.**

### 6a. Two-world authorization model

From `src/continuation.zig` (lines 176-220):

```zig
pub const GroveSpheres = struct {
    worlds: std.ArrayListUnmanaged(BeliefSet),
    // worlds[0] = actual world (ground truth authorization)
    // worlds[1] = worker's belief about their authorization
    // worlds[2..] = hypothetical scenarios (what-if analysis)
};
```

**Actual world (sphere 0):** What the system KNOWS the worker is authorized to do.

```zig
var actual = BeliefSet.init(allocator);
try actual.expand(.{ .proposition = "can-enter-property" });
try actual.expand(.{ .proposition = "can-spend-up-to-200" });
try actual.expand(.{ .proposition = "can-purchase-listed-items" });
// NOT present: "can-modify-order", "can-access-payment-info"
```

**Worker's belief world (sphere 1):** What the worker THINKS they're authorized to do.

```zig
var worker_belief = BeliefSet.init(allocator);
try worker_belief.expand(.{ .proposition = "can-enter-property" });
try worker_belief.expand(.{ .proposition = "can-spend-up-to-200" });
try worker_belief.expand(.{ .proposition = "can-purchase-listed-items" });
try worker_belief.expand(.{ .proposition = "can-substitute-items" }); // ← EXTRA belief!
```

**Divergence detection:** `actual.entails("can-substitute-items")` returns `false`, while `worker_belief.entails("can-substitute-items")` returns `true`. The system detects the discrepancy.

### 6b. AGM revision when authorization changes

The existing AGM operations (lines 137-175) handle authorization updates:

**Expansion (grant new permission):**
```zig
// Requester authorizes item substitution
try actual.expand(.{ .proposition = "can-substitute-items" });
// Worker belief now matches — no longer divergent
```

**Contraction (revoke permission):**
```zig
// Requester revokes spending authority
actual.contract("can-spend-up-to-200");
// Worker still believes they can spend — DIVERGENCE
// System must notify worker: their belief is stale
```

**Revision (change belief to match reality):**
```zig
// Worker learns they can't substitute (Levi identity: contract ¬p, then expand p)
try worker_belief.revise(.{ .proposition = "not-can-substitute-items" });
// Now worker belief: "not-can-substitute-items" is present
// "can-substitute-items" was removed by the Levi identity
```

From `BeliefSet.isConsistent()` (lines 162-175):


**Application:** If a worker's belief set is inconsistent (e.g., they believe both "can-enter-property" and "not-can-enter-property"), the system flags the task for review. This catches:

### 6d. Entrenchment ordering for priority

From `Belief` (lines 122-124):


**For authorization:** Entrenchment determines which beliefs survive contraction:
- `"can-enter-property"` (entrenchment: 100) — core permission, hard to revoke

## 7. Data Flow: End-to-End Task Lifecycle

```
1. TASK CREATION
   Requester → ContinuationState.init(steps) → ContinuationId
                Pipeline.init(steps, step_fns)
                ContinuationExecutor.pause(cmd) → PromiseKey
                BeliefSet.init() → actual authorization sphere
                GroveSpheres.addWorld(actual)

2. WORKER MATCHING
   SplitMixTrit.opine(worker_seed, task_description) → worker_trit
   Step.trit vs worker_trit → compatibility check
   TriadicGenerator.opine(seed, proposition) → (trit, color) for UI

3. TASK DISPATCH (via OCapN CapTP)
   ContinuationState.toSyrup(allocator) → syrup.Value
   syrup.Value.encode(writer) → bytes on wire
   PromiseKey sent to worker as unforgeable capability

4. WORKER EXECUTION
   Worker receives PromiseKey → phase 0→2
   Pipeline.step(input) → StepResult
     .success → advance to next step
     .yield → pause (worker needs to wait)
     .failure → task failed

5. DELEGATION (humans hiring humans)
   Worker calls executor.pause(sub_cmd) → PromiseKey_child
   stack_depth += 1
   createHomotopyPath(parent, child) → traces delegation chain
   Queue-balance audit and optional SplitMixTrit combiner check at each delegation

6. COMPLETION
   Pipeline.isComplete() → true
   PromiseKey.phase → 3
   BeliefSet consistency check → validate authorization wasn't violated
   Account hold → capture payment or release

7. CONSERVATION AUDIT
   SplitMixTrit.isConserved() → additive combiner stayed exact?
   Every Generator (+1) paired with Validator (-1)?
   Queue-level GF(3) balance tracked separately?
```

## 9. GF(3) Conservation Properties

### 9a. Per-task conservation

Every task that involves creation (+1) MUST have a corresponding verification (-1). The system enforces this by:

1. When a Generator step completes, the Pipeline automatically appends a Validator step
2. When a task tree's GF(3) sum drifts from 0, the system spawns balancing tasks
3. The `SplitMixTrit.isConserved()` check can run at delegation boundaries to verify
   the PRNG combiner itself is behaving algebraically

### 9b. Per-worker conservation

Over time, each worker's task history should approach GF(3) balance:
- A worker who only generates (+1) will be offered validation tasks (-1)
- The `SplitMixTrit.trit_sum` accumulates per-worker, driving assignment logic

### 9c. System-wide conservation

The `TriadicGenerator` in `splitmix_trit.zig` forwards the underlying combiner check:

```zig
pub fn isConserved(self: *const TriadicGenerator) bool {
    return self.trit_gen.isConserved();
}
```

**Invariant:** the underlying triadic PRNG combiner remains exact in GF(3). If you want
the entire task system to maintain net-zero balance, that must be checked at the queue or
task-graph layer rather than inferred from `SplitMixTrit` alone.

## 11. Summary

Pathway A requires **zero new modules**. The existing zig-syrup infrastructure provides:

1. **PromiseKey** = task assignment (unforgeable capability, phase-tracked lifecycle)
2. **ContinuationState** = full task context (steps, metadata, registers, all Syrup-serializable)
3. **Trit** = worker role (Generator/Coordinator/Validator, GF(3)-balanced)
4. **ContinuationExecutor.pause()** = humans hiring humans (recursive PromiseKey derivation, HomotopyPath chains, stack_depth tracking)
5. **BeliefSet + GroveSpheres** = authorization belief tracking (actual vs believed, AGM revision, consistency checking)

The Syrup wire format handles all serialization. GF(3) balancing in the task graph can
ensure every creation is paired with verification, while `SplitMixTrit` separately ensures
its additive PRNG combiner remains algebraically faithful. The OCapN capability model means
possession of a PromiseKey is the only authorization needed — no passwords, no OAuth, just
capabilities.
